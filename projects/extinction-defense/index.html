Introduction

Extinction Defense is a prehistoric themed tower defense game that I am building from scratch in C++ using SDL2. Instead of using a full game engine like Unity or Godot, I wanted to try to better understand the underlying systems that really make a game work.

The basic idea is simple: dinosaurs are your towers and you use them to defense against increasingly difficult waves of enemies. Under the hood, however, the project turned into a MUCH larger excercise in C++ architecture, real-time simulation, asset management, build systems, and cross-platform deployment.

I could have made the game much faster in an existing engine, but that wasn't really the point of the project. A big reason why I started Extinction Defense was to get better at C++ by building something large enough where organization and archetecture really mattered.



Building A Game Without a Game Engine

SDL2 gives me a window, renderer, input handling, audio support, and some other lower level functionality, but most of the actual game behavior still has to be written by me. The game runs around a traditional real-time update and render loop. Each frame I process input, update the current game state, update waves towers, enemies, and projectiles, and then render the result to the screen.

Working this way forced me to think a lot more about program state than I would have if an engine were handling everything for me. Menus, gameplay, settings, pausing, wave progression, tower selection, and other parts of the game all have to transition cleanly without interfering with one another.

Using SDL2 instead of a full game engine was also a tradeoff. It significantly increased the amount of work required to reach a playable product, but it gave me much more control over the systems underneath the game and forced me to understand how they fit together. Throughout the project I've had to make similar decisions about when something was worth building myself and when I should use an existing tool or library.

It also gave me experience working directly with SDL2 along with SDL_image, SDL_ttf, and SDL_mixer for graphics, fonts, and audio.



Tower and Combat Systems

There are currently 12 different dinosaur towers, each with their own unique attack patterns. Some are straightforward single-target attackers, while others have completely different mechanics, such as splash damage, burst attacks, economy towers, attack-speed boost towers, manual artillery targeting, and towers that can be repositioned after being placed.

Each tower also has two separate five level upgrade paths, generally split between damage and utility. The upgrades modify the individual tower that the player placed rather than changing some global definition.

That distinction is actually a core part of what makes Extinction Defense work; Separate classes for new tower definitions and runtime-state towers allow me to differentiate between all different towers.

From the beginning, I wanted the game to be easy to understand, but still give the player meaningful choices. Each dinosaur should have an obvious purpose, but there shouldn't be one tower that is always the correct answer. I wanted players to slowly understand how the different systems interact and eventually build strategies of their own.



Projectiles and Predictive Targeting

The projectile system became one of the more complicated parts of the game. Normal projectiles don't simply aim at where an enemy currently is. The game looks at the enemy's movement and calculates where it should be by the time the projectile reaches it. The projectile then fires toward that predicted position.

This mean working with positions, velocities, distance calculations, and timing rather than just making a projectile follow an enemy every frame.

Projectiles also snapshot the relevant tower stats when they are fired, so that there are no issues with upgrades changing projectiles mid-attack.

I also cventralized enemy damage into one system so that mechanics such as armor, slows, death, and rewards aren't inndependently handled by each tower.



Enemies and Wave Progression

The game currently includes 18 enemy types and a complete 120 wave progression.

Enemies start fairly simple, but later waves introduce enemies with different roles and abilities. Some are fast, some are heavily armored, some heal nearby units, and others provide support effects.

The wave system uses a state machine to keep track of whether the game is waiting for the player, actively spawning enemies, or waiting for the remaining enemies to be cleared.

Making 120 waves also introduced a HUGE challenge: balancing. Keeping track of health, money, damage, upgrades, and progression made balancing the game really hard. However, it ultimately gave me a lot more experience with working with products rather than just code.



From Project to Product

One of the most important things that I learned from this project was to constantly think about the user. It doesn't matter if I could understand exactly how the program works, if the user can't understand it right away.

Along with that came the realization that there is no point in making a game if it isn't fun to play! I was constantly thinking about how to make the game more fun, using my friends as playtesters in the very beginning.

I also learned that a product is more than just the code that makes it work. Everything that goes into a product isn't just "making something", but it is about creating something useful that real people would want/need to use.



Playtesting

While I am still in the process of playtesting, I can already see the benefits. My current playtesting loop is Build -> Observe -> Identify Issues -> Prioritize -> Change -> Test Again.

Having other people play the game has already changed the way develop it. Things that seemed completely obvious to me were confusing to others playing for the first time. Instead of explaining what the player was "supposed to do", I started paying attention to where they hesitated and what they misunderstood.

That feedack helped me decide what needed work instead of just adding whatever feature sounded interesting to me next.



Conclusions & Future

Extinction Defense is still very much a work in progress, but I am proud of how far it has come. It is now in a fully playable state, so I'm now working on adding more content, polishing the UI, and making the game overall feel more "professional".

Another challenge was deciding what not to work on. It was easy to come up with new towers, animations, maps, and mechanics, but adding features forever wouldn't get me any closer to having a finished product. My priority became getting the complete gameplay loop working first. Once the game reached a fully playable state, I could shift more attention toward UI, presentation, balancing, and the other things that affect how finished the product feels.

There are release builds available on Github for Windows/Mac/Linux, and I am always looking for more playtesters, so see the Contact page on my site if interested.

There is still a lot of work to do, but I am excited to continue working on this project and eventually getting it out there to real users around the world!
